# Чек-лист готовности AI-системы к запуску

## Назначение

Финальная проверка go/no-go перед выводом AI-системы в продакшен. Это последний контрольный пункт
перед запуском, не замена оценки риска на более ранней стадии.

## Контекст дела

Прочитай `~/.claude/plugins/config/claude-for-legal-ru/regulirovanie-ii/CLAUDE.md`. Файла нет или
в нём остались `[ЗАПОЛНИТЬ]` — стоп: «Плагину нужна настройка, запусти
`/regulirovanie-ii:cold-start-interview`.»

Система должна уже быть в `reestr-sistem-ii` (иначе сначала занеси её туда). Если включён режим
`vedenie-del` и есть активное дело — результат пиши в папку дела.

## Предусловия

- Разработка AI-системы завершена.
- Если система обрабатывает ПДн — `personalnye-dannye:use-case-triage` пройден; если триаж
  потребовал оценку вреда субъектам — `personalnye-dannye:pdn-assessment` завершён.
- Техническое тестирование выполнено.
- Заинтересованные подразделения готовы к запуску.

## Workflow

### Шаг 1. Согласования

```markdown
## Проверка согласований
- [ ] `personalnye-dannye:use-case-triage` пройден (если обрабатывает ПДн): [решение]
- [ ] `personalnye-dannye:pdn-assessment` завершён и подписан (если требовался по триажу): [ссылка,
      дата]
- [ ] Ответственный за AI в организации одобрил: [подпись]
- [ ] Ответственный за комплаенс/ПДн одобрил (если применимо): [подпись]
- [ ] Служба информационной безопасности одобрила: [подпись]
- [ ] (Для материально значимой системы) outside-адвокат ФПА провёл ревью: [подпись]
- [ ] (Для материально значимой системы) одобрение руководства/совета директоров: [подпись, если
      требуется по внутреннему порядку]

Пробел в любом обязательном пункте — стоп до устранения.
```

### Шаг 2. Технические меры защиты

```markdown
## Технические меры

### Перед запуском
- [ ] Валидация входных данных реализована
- [ ] Фильтрация вывода / модерация контента настроена
- [ ] Ограничение частоты запросов настроено
- [ ] Аутентификация/авторизация проверена
- [ ] Логирование реализовано без утечки ПДн в логи
- [ ] Шифрование при передаче и хранении проверено
- [ ] Контроль доступа пересмотрен
- [ ] План резервного копирования / восстановления после сбоя
- [ ] (Для LLM) оценка уверенности и пороги настроены
- [ ] (Для LLM) откат к человеку при низкой уверенности настроен

### Устойчивость к манипуляциям (если применимо)
- [ ] Тестирование инъекций в промпт (для LLM)
- [ ] Тестирование обхода модели (для security-систем)
- [ ] Защита от отравления данных
```

### Шаг 3. Соответствие требованиям к данным

```markdown
## Данные

### 152-ФЗ (если обрабатывает ПДн)
- [ ] Правовое основание задокументировано
- [ ] Специфические согласия собраны там, где требуются
- [ ] Локализация подтверждена (хранение в РФ — ст. 18 ч. 5)
- [ ] Для трансграничной передачи — основание и, если применимо, уведомление РКН
- [ ] Срок хранения данных определён
- [ ] Механизм удаления ПДн реализован
- [ ] Права субъекта (доступ, удаление) реализованы — см. `personalnye-dannye:subject-request`
- [ ] Оценка вреда субъектам (п. 5 ч. 1 ст. 18.1) на месте, если требовалась

### Обучающие данные
- [ ] Источники лицензированы надлежащим образом (см. `proverka-obuchayushchih-dannyh`, если
      система обучена/дообучена организацией)
- [ ] Нарушений авторских прав не выявлено
- [ ] Утечки ПДн в обучающих данных без правового основания не выявлено
- [ ] Чувствительный контент отфильтрован

### Продакшен-данные
- [ ] Источники данных задокументированы
- [ ] Качество данных проверено
- [ ] Настроено обнаружение аномалий
```

### Шаг 4. Мониторинг

```markdown
## Мониторинг

### Производительность
- [ ] Дашборд метрик точности/качества
- [ ] Метрики задержки/пропускной способности
- [ ] Мониторинг частоты ошибок
- [ ] Пороги оповещений настроены

### Дрейф и справедливость (если применимо)
- [ ] Отслеживание производительности по подгруппам
- [ ] Обнаружение дрейфа по точности
- [ ] Обнаружение дрейфа по справедливости
- [ ] Периодический повторный аудит запланирован

### Безопасность
- [ ] Обнаружение аномальных паттернов запросов
- [ ] Мониторинг неудачных попыток аутентификации
- [ ] Обнаружение состязательных входных данных

### Логи
- [ ] Аудит-логи реализованы
- [ ] Действия пользователей отслеживаются (для рассмотрения споров)
- [ ] Логи неизменяемы / защищены от подмены
- [ ] Срок хранения логов соответствует требованиям
```

### Шаг 5. Реагирование на инциденты

```markdown
## Реагирование на инциденты
- [ ] План реагирования задокументирован
- [ ] Дежурство установлено
- [ ] Цепочка эскалации ясна (технический уровень → ответственный за AI → руководство)
- [ ] Процедура коммуникации с пользователями при инциденте
- [ ] Процедура уведомления регулятора, если применимо (напр. РКН — при инциденте с ПДн)
- [ ] Процесс разбора после инцидента
- [ ] Классификация серьёзности (P0/P1/P2/P3)
- [ ] Типовые инциденты отработаны на учении (рекомендуется)
```

### Шаг 6. Уведомления пользователям

См. `/regulirovanie-ii:uvedomlenie-polzovatelej-ii` для полного разбора.

```markdown
## Уведомления пользователям
- [ ] Использование AI раскрыто пользователям там, где применимо
- [ ] Право на пересмотр решения человеком разъяснено (для автоматизированных решений по ст. 16
      152-ФЗ)
- [ ] Политика обработки данных обновлена с учётом AI
- [ ] Пользовательское соглашение обновлено (особенно если применима ст. 10 ч. 1 243-ФЗ)
- [ ] FAQ/справка подготовлены
- [ ] Служба поддержки обучена работе с вопросами про AI
```

### Шаг 7. Отношения с вендором (если система на основе стороннего сервиса)

```markdown
## Вендор
- [ ] Договор подписан (см. `/regulirovanie-ii:proverka-postavshchika-ii`)
- [ ] Условия обработки ПДн согласованы (если применимо)
- [ ] Отсутствие обучения на наших данных подтверждено (или согласованный opt-out)
- [ ] Место обработки данных подтверждено
- [ ] SLA определён
- [ ] План выхода / переносимости данных
- [ ] Резервный вендор определён (для санкционного риска / риска непрерывности)
```

### Шаг 8. Обучение персонала

```markdown
### Внутренние пользователи
- [ ] Первичное обучение проведено
- [ ] Ознакомление с политикой допустимого использования (см. `politika-ispolzovaniya-ii`)
- [ ] Порядок сообщения о проблемах понятен

### Операторы (команда, эксплуатирующая систему)
- [ ] Техническое обучение по эксплуатации
- [ ] Обучение реагированию на инциденты
- [ ] Обучение мониторингу дрейфа/справедливости

### Клиентские подразделения
- [ ] Как объяснять клиентам использование AI
- [ ] Обучение порядку рассмотрения споров/апелляций
- [ ] Процедуры эскалации
```

### Шаг 9. План поэтапного вывода

```markdown
### Подход
- [ ] Постепенный / пилотный / полный вывод? [...]
- [ ] Конкретные фазы запланированы
- [ ] Процедура отката определена
- [ ] Критерии успеха на каждую фазу

### Первичный мониторинг
- [ ] Усиленный мониторинг на первые 30 дней
- [ ] Регулярные встречи по обзору (ежедневно/еженедельно)
- [ ] Порог для приостановки вывода при проблемах

### Коммуникация
- [ ] Заинтересованные стороны проинформированы
- [ ] (Для клиентской системы) план коммуникации с пользователями
- [ ] Внутренние команды готовы
```

### Шаг 10. Итоговое решение

```markdown
## Решение

[GO / NO-GO / УСЛОВНЫЙ GO]

### Если условный GO
Конкретные условия до финального запуска:
- [ ] [условие 1]
- [ ] [условие 2]

Повторная проверка запланирована: [ДД.ММ.ГГГГ]

### Если NO-GO
Причины:
- [...]

План устранения:
- [...]

Повторная проверка: [ДД.ММ.ГГГГ]
```

## Первые 30 дней после запуска

```markdown
### Ежедневно
- [ ] Дашборд мониторинга просмотрен
- [ ] Журнал инцидентов просмотрен
- [ ] Каналы обратной связи от пользователей проверены

### Еженедельно
- [ ] Встреча команды (техническая + бизнес + комплаенс)
- [ ] Анализ трендов производительности
- [ ] Разбор произошедших инцидентов

### После 30 дней
- [ ] Пересмотр оценки вреда субъектам, если проводилась — актуальна ли ещё
- [ ] Фактическая производительность против прогнозной
- [ ] Удовлетворённость пользователей (для клиентской системы)
- [ ] Обновлённая оценка риска
```

## Чего не делает

- Не заменяет `personalnye-dannye:pdn-assessment` там, где он требуется по существу, и не вводит
  формальную «AI Impact Assessment» — такого института российское право не предусматривает.
- Не проводит техническое тестирование — это QA/data science.
- Не заменяет заключение outside-адвоката ФПА для материально значимых систем.

---

Проверки перед выдачей:
- [ ] Решение GO/NO-GO/условный GO указано прямо, а не оставлено подразумеваемым
- [ ] Для систем без обработки ПДн явно отмечено, что формальная оценка вреда субъектам не
      применима — не помечено пропуском без объяснения
- [ ] Уведомления пользователям и договор с вендором проверены со ссылкой на соответствующий
      скилл плагина, а не продублированы здесь заново
