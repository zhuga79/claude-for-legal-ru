# Участие в проекте

Проект делают практикующие юристы. Писать код не обязательно — большая часть
работы здесь это текст: нормы, их редакции, формулировки, чеклисты.

Прежде чем предлагать правку, прочитайте `BRAIN.md` — там правила работы,
и `TASKS.md` — там видно, что уже в работе.

---

## Главное правило

**Самый опасный дефект здесь — не выдуманная норма, а норма в устаревшей
редакции.** Выдуманную видно сразу. Устаревшая внутренне непротиворечива,
выглядит грамотно и вычиткой не ловится — а на выходе даёт неверную
квалификацию.

Поэтому от любого утверждения о праве требуется три вещи:

1. **Ссылка на норму** — статья, пункт, часть. Не «по ГК», а «п. 2 ст. 434 ГК РФ».
2. **Редакция и дата** — на какую дату норма проверена по первоисточнику.
3. **Тег происхождения** — откуда сведение взялось:
   - `[сверено ДД.ММ.ГГГГ]` — открывали первоисточник и сверяли текст
   - `[проверить по первоисточнику]` — взято из вторичного источника
   - `[знания модели — проверить]` — сгенерировано моделью, не сверено

Тег говорит о **происхождении**, а не об уверенности. `[знания модели]` —
это не «наверное верно», это «никто не открывал закон».

Предложение без ссылки на норму закрывается без обсуждения. Это не
формальность: непроверяемое утверждение в юридическом скилле опаснее, чем
отсутствие скилла.

## Три способа участвовать

### 1. Через issue — если не работаете с git

Самый частый и самый полезный вклад. Заведите issue по шаблону:

- **Неверная норма** — скилл ссылается на статью, которой нет, или толкует её неправильно
- **Устаревшая редакция** — норма изменилась, скилл про это не знает
- **Пробел** — контур не покрывает ситуацию, которая встречается в практике
- **Новый скилл или плагин** — предложение с обоснованием, зачем он нужен

Опишите, что скилл выдаёт сейчас и что должен, со ссылкой на норму. Этого
достаточно — оформит кто-то другой.

### 2. Через веб-редактор GitHub — правка одного файла

Кнопка «Edit this file» в интерфейсе GitHub создаёт ветку и pull request
сама. Git локально не нужен. Подходит, чтобы поправить формулировку,
обновить редакцию нормы, дописать пункт в чеклист.

### 3. Через pull request — если работаете с git

Обычный порядок: форк, ветка, PR. Чеклист в шаблоне PR.

## Что не принимается

- **Юридическая консультация по конкретному делу.** Проект делает
  инструменты, а не разбирает споры участников.
- **Персональные данные в любом виде.** Ни имён клиентов, ни ИНН, ни номеров
  дел, ни реквизитов, ни выдержек из переписки. Примеры пишутся обезличенно:
  «ООО „Ромашка“», «Заказчик», «сторона А». Это условие участия, а не
  пожелание — за адвокатскую тайну отвечает тот, кто её раскрыл.
- **Готовые документы клиентов** как шаблоны — даже обезличенные, если
  документ узнаваем.
- **Утверждения о праве без ссылки на норму** — см. выше.

## Как устроено ревью

Правовое существо проходит **две независимые стадии** — это уже действующий
порядок проекта, а не требование, придуманное для внешних участников:

1. **Правовое ревью** — роль `lawyer` или `compliance`: верна ли норма, верна
   ли редакция, верна ли квалификация, нет ли пропущенного основания.
2. **Независимое ревью другой моделью другого провайдера** — чтобы не
   получить коррелированные слепые пятна. Одна и та же модель, проверяя
   себя, вносит ошибки в те же абзацы, которые правит.

Merge возможен после обеих. Если правка касается стыка контуров — например,
налоги и договор, — подключается режим `council` с несколькими ролями:
одна роль решение не принимает.

Полный порядок приёма:

| Шаг | Роль | Что проверяет |
|---|---|---|
| 1 | `triage` | ссылка на норму, дата сверки, тег происхождения, дубли, отсутствие ПД |
| 2 | `lawyer` / `compliance` | верна ли норма, верна ли **редакция**, верна ли квалификация |
| 3 | `reviewer` | независимая проверка моделью другого провайдера |
| 4 | `maintainer` | решение о merge и ответ автору |

Налоговая квалификация — всегда к `tax-advisor`: ни `lawyer`, ни
`compliance` налог не считают. Персональные данные и регуляторные
процессы — к `compliance`.

**Что означает merge.** Что правка прошла ревью, а не что она гарантированно
верна. Статус каждого скилла — в `TASKS.md`. Не всё прошло обе стадии, и это
там честно отражено.

## Технические гейты

Зелёный CI — не ревью, а гигиена. Он проверяет ровно четыре вещи: манифест
маркетплейса и существование объявленных плагинов, отсутствие контактов и
реквизитов в тексте, наличие frontmatter у каждого скилла, наличие
дисклеймера в README. Правовое существо не проверяется ничем автоматическим —
для этого и нужны стадии выше.

**Локальный хук перед коммитом.** Ставится один раз:

```bash
./tools/install-hooks.sh
```

Хук проверяет индекс на персональные данные и секреты двумя слоями:
обезличенные признаки (почта, телефон, ИНН/ОГРН, СНИЛС, номер счёта, ключи
API и приватные ключи) и — у мейнтейнеров — личный список имён клиентов и
дел из файла **вне репозитория**. Личный список в git не попадает никогда.
Если `brain-guard` в системе нет, работает встроенная проверка на python3 —
внешнему участнику ставить ничего не нужно.

Именной слой применяет правила **целыми словами**: список имён,
применяемый подстрокой, совпадает внутри обычных слов («доследственной»,
«Документы») и блокирует каждый коммит, а гейт, срабатывающий всегда,
обходят через `--no-verify`. Гейт, который научились обходить, хуже
отсутствующего.

## Куда класть изменения

```
<плагин>/
├── CLAUDE.md              правила плагина
└── skills/
    └── <имя-скилла>/
        └── SKILL.md       сам скилл
```

Плагины соответствуют контурам практики: `dogovornoe-pravo`,
`korporativnoe-pravo`, `trudovoe-pravo`, `sudebnyj-process`,
`nalogovoe-pravo`, `personalnye-dannye`, `intellektualnaya-sobstvennost`,
`nekommercheskie-organizacii`, `nedvizhimost`, `protivodejstvie-otmyvaniyu`,
`regulirovanie-ii`, `gosudarstvennye-zakupki`, `zaschita-prav-potrebitelej`,
`administrativnoe-pravo`, `regulyatornyj-monitoring`, `vedenie-del`.

Новый контур заводится отдельным плагином, а не свалкой в существующий.
Прежде чем заводить — issue с обоснованием: какие задачи закрывает, почему
не помещается в существующий контур.

Файл, изменённый относительно оригинала `anthropic/claude-for-legal`,
помечается в заголовке: `Локализация РФ на основе <оригинальный путь>`.

## Правовая сторона вклада

Проект под **Apache License 2.0** — производная работа от
`anthropic/claude-for-legal` © Anthropic PBC (см. `LICENSE` и `NOTICE`).

Отправляя правку, вы соглашаетесь, что она распространяется на тех же
условиях, и подтверждаете, что вправе её передать: текст ваш либо взят из
источника, допускающего такое использование. Нормативные акты РФ объектами
авторского права не являются (ст. 1259 ГК РФ), а вот комментарии, обзоры
практики и материалы правовых баз — являются. Пересказ своими словами со
ссылкой на источник — нормально; копирование абзацев из платной базы — нет.

Отдельного CLA нет: подписание Apache-2.0 через сам факт PR (inbound=outbound)
достаточно.

## Ответственность

Вывод любого скилла — **проект для проверки практикующим юристом**. Подавать
в суд, подписывать и сдавать в госорган подготовленное здесь можно только
после проверки человеком. За правовые позиции отвечает использующий плагин
юрист, а не плагин и не авторы форка.

Участие в проекте не создаёт отношений «юрист — клиент» ни между
участниками, ни с пользователями.
