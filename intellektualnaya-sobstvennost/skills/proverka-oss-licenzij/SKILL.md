# /proverka-oss-licenzij

Разбирает лицензии открытого исходного кода в продукте, называет обязательства и помечает
риски. Это экспресс-проверка, **не полный аудит открытого кода** для существенной поставки —
для него нужен инструментальный скан (SCA) и профильный консультант.

## Контекст дела

Прочитай `~/.claude/plugins/config/claude-for-legal-ru/intellektualnaya-sobstvennost/CLAUDE.md`.
Файла нет или остались `[ЗАПОЛНИТЬ]` в разделе «Открытый исходный код» — стоп: «Плагину нужна
настройка, запусти `/intellektualnaya-sobstvennost:cold-start-interview`».

Если включён режим `vedenie-del` и есть активное дело — выводы пиши в папку дела.

## Шаг 1. Зафиксируй сценарий поставки

Обязательства copyleft срабатывают в основном при **распространении**, а не при использовании.
Определи, что из этого:

- внутренний инструмент, наружу не отдаётся;
- SaaS / сетевой сервис (важно для AGPL — сетевое использование приравнено к распространению);
- поставляемый продукт (дистрибутив, десктоп, мобильное приложение, прошивка);
- сам открытый продукт.

## Шаг 2. Собери зависимости

Прямые и транзитивные, с лицензией каждой. Инструменты: `pip-licenses` (Python),
`license-checker` (Node.js), `mvn license:add-third-party` (Java/Maven), `go-licenses` (Go);
для C/C++ — вручную либо инструментальный скан.

## Шаг 3. Классифицируй лицензии

**Разрешительные (permissive).** MIT, BSD 2-Clause / 3-Clause, Apache 2.0, ISC. Обязательства
минимальны: сохранить уведомление об авторских правах и текст лицензии. Apache 2.0
дополнительно: патентная оговорка, файл NOTICE, пометка изменений. BSD 3-Clause: запрет
использовать имена авторов для продвижения. Свободно применимы в проприетарном продукте.

**Слабый copyleft.** LGPL 2.1/3.0, MPL 2.0, EPL, CDDL. Изменения в самих copyleft-файлах
остаются под той же лицензией; комбинация с проприетарным кодом допустима при выполнении
условий (для LGPL — возможность заменить библиотеку, обычно динамическая линковка).

**Сильный copyleft.** GPL 2.0/3.0, AGPL 3.0. Производное произведение при распространении
должно распространяться под той же лицензией с предоставлением исходного кода. AGPL
распространяет это на сетевое использование. Совместимость с проприетарной поставкой —
только через существенную реорганизацию или замену компонента.

**Source-available и нестандартные.** BSL, SSPL и подобные — **не** открытый исходный код в
строгом смысле, содержат ограничения; читать текст каждой.

**Общественное достояние.** CC0, Unlicense.

## Шаг 4. Совместимость

Разнонаправленные обязательства дают конфликт. Типичные:

| Лицензия A | Лицензия B | Совместимость |
|---|---|---|
| MIT / BSD | GPL 3.0 | да (в одну сторону — под GPL) |
| Apache 2.0 | GPL 2.0 | **нет** (патентная оговорка) |
| Apache 2.0 | GPL 3.0 | да |
| GPL 2.0 (только) | GPL 3.0 | **нет** (разные версии без «or later») |
| LGPL | GPL | да (LGPL повышается до GPL) |

Помечай несовместимости отдельно.

## Шаг 5. Обязательства по российскому праву

Открытый исходный код по российскому праву — это лицензионный договор о предоставлении права
использования произведения (ст. 1235, 1286 ГК); программа для ЭВМ охраняется как литературное
произведение (ст. 1259, 1261 ГК). Российское право признаёт конструкцию **открытой лицензии**
(ст. 1286.1 ГК) — договор присоединения, условия которого изложены на экземпляре или в
электронном виде, с умолчаниями (безвозмездность, для программ — весь срок охраны, территория
всего мира).

**Автоматическое приравнивание конкретной западной OSS-лицензии к открытой лицензии по
ст. 1286.1 некорректно** — вопрос применимого права и соответствия существенным условиям
ст. 1235 ГК решается отдельно по каждой лицензии (см.
`/intellektualnaya-sobstvennost:rasporyazhenie-pravami`, шаг про открытую лицензию).
Содержательный разбор обязательств copyleft конкретной лицензии при поставке конкретного
продукта — отдельная предметная работа, а не общий шаблон.

## Шаг 6. Реестр российского ПО и ИТ-аккредитация

Для включения в единый реестр российских программ (Постановление Правительства РФ от
16.11.2015 № 1236, последняя редакция — 09.12.2025) `[сверено 27.08.2026 — условия включения
менялись, проверять действующую редакцию Правил на дату подачи]`:

- программа должна быть российского происхождения по критериям Правил;
- компоненты открытого кода допустимы, но не должны определять основную функциональность и
  должны быть корректно задокументированы и лицензированы;
- в описании для реестра открытые компоненты и собственный вклад раскрываются явно.

Налоговые льготы для аккредитованных ИТ-компаний (налог на прибыль, тариф страховых взносов)
и льготы по операциям с ПО из реестра — **зона роли `tax-advisor`**, плагин их не считает.

Для государственных и корпоративных заказчиков действует приоритет отечественного ПО
(запрет допуска иностранного ПО при закупках) — если продукт сильно зависит от иностранного
открытого кода, это может быть минусом при квалификации происхождения `[знания модели —
проверить по действующей редакции ограничений на дату]`.

## Чего не делать

- Не выдавать экспресс-проверку за полный аудит открытого кода — для существенной поставки
  нужен инструментальный скан.
- Не квалифицировать произвольную OSS-лицензию как открытую лицензию по ст. 1286.1
  автоматически.
- Не давать содержательное заключение по copyleft-обязательствам конкретной лицензии как
  часть этого скилла — это отдельная работа.
- Не считать налоговые льготы ИТ-компаний и льготы по реестру ПО — это `tax-advisor`.
- Не называть критерии реестра российского ПО и ограничения по закупкам по памяти —
  сверять действующую редакцию на дату.
