# /review

Проверяет входящий договор против плейбука в `~/.claude/plugins/config/claude-for-legal-ru/dogovornoe-pravo/CLAUDE.md`. Определяет структуру по заголовкам, выбирает скилл(ы) и — если включён confirm_routing — уточняет у пользователя до начала.

## Инструкции

1. **Загрузи `~/.claude/plugins/config/claude-for-legal-ru/dogovornoe-pravo/CLAUDE.md`.** Если есть плейсхолдеры — остановись: «Сначала запустите `/dogovornoe-pravo:cold-start-interview` — мне нужно изучить ваш плейбук, чтобы проверять против него».

   Прочитай также `## Настройки ревью` → `confirm_routing`. Если поля нет — считай `true`.

2. **Получи договор:** из пути к файлу, ссылки на Диск или вставленного текста. Если ничего не дали — спроси.

3. **Прочитай структуру — сначала заголовки.** До тела извлеки: название основного договора (напр., «Договор возмездного оказания услуг», «Договор поставки», «Соглашение о конфиденциальности») и все приложения/спецификации/допсоглашения. Это сигнал маршрутизации. Не полагайся только на ключевые слова в теле — 40-страничный договор со словом «конфиденциально» повсюду не является NDA.

4. **Выбери скилл(ы) по структуре.**

   | Заголовок документа/раздела содержит | Скилл |
   |---|---|
   | Соглашение о конфиденциальности, NDA, о неразглашении (как *основной* документ) | **nda-review** |
   | Договор оказания услуг, подряда, поставки, поручения, агентский, лицензионный | **vendor-agreement-review** |
   | Подписка/SaaS/облачный сервис/доступ к ПО с автопролонгацией и периодическими платежами | **vendor-agreement-review**, затем **saas-msa-review** поверх (квалификация: лицензия ст. 1235, 1286 / услуги гл. 39 / смешанный п. 3 ст. 421; абонентская модель ст. 429.4; присоединение ст. 428; одностороннее изменение ст. 310, 424; SLA ст. 401, 330, 394; данные и обучение моделей; выход и выгрузка; зарубежный провайдер) |
   | Соглашение об обработке ПД / поручение на обработку (приложение) | пометка для **vendor-agreement-review** → раздел «Персональные данные» (ч. 3 и ч. 5 ст. 6, ч. 3.1 ст. 21, ст. 12, ч. 5 ст. 18 ФЗ-152) |

   Может применяться несколько скиллов. Если структура неоднозначна после заголовков — прочитай первые 1–2 страницы тела, затем остановись и маршрутизируй.

   **Порядок для SaaS/подписки строгий:** `saas-msa-review` — надстройка, а не замена. Сначала общий проход `vendor-agreement-review` (заключённость, ответственность, заверения, ПД-обвязка, подсудность), затем SaaS-надстройка. Наоборот — получится SaaS-раздел без базового чек-листа.

5. **Подтверди маршрутизацию, если включено.** Если `confirm_routing` = `true`:

   ```
   Проверю это как: [тип(ы) договора].
   Документы:
   - [Название основного договора] → [скилл]
   Продолжаю? (да / поправьте маршрут)
   ```

6. **Запусти выбранный скилл(ы)** (`vendor-agreement-review`, `nda-review`, `saas-msa-review`), собери в единый меморандум. Шапка, теги источников и заметка ревьюера — из `## Выводы` конфига.

7. **Закрой деревом следующих шагов** из `## Выводы`. Если предлагаешь ветку «сводка для бизнеса» —
   она вызывает `stakeholder-summary` уже ПОСЛЕ того, как этот меморандум готов (не вместо него).

8. **Если пришла новая редакция уже проверенного договора или допсоглашение к нему** — прежде чем
   гонять полный чек-лист заново, предложи `amendment-history`: он покажет, что именно изменилось
   относительно версии, которую уже проверяли, включая формальную сторону допсоглашения и тихие
   изменения смежных пунктов. Полный повторный проход остаётся доступен, если пользователь хочет
   именно его.

## Примеры

```
/dogovornoe-pravo:review ./dogovor-postavki.docx
```
```
/dogovornoe-pravo:review
Проверь этот NDA от контрагента [вставленный текст]
```
```
/dogovornoe-pravo:review ./oferta-saas.pdf
Мы покупаем подписку, продление через месяц — на что смотреть
```
